# Internal D1 poll admission — #238

`src/d1.ts` adds a native D1 counterpart to the [SQLite laboratory](README.md).
It supports the same new creator-closable polls, ballots, creator closes,
ordinary `intel`, retained capacity and exact historical receipts. This is a
private source-checkout adapter. **No production route imports it; no production
migration, policy defaults, npm release or availability change is included.**
The full [admission design](../../docs/public-write-admission.md) and #229/#238/#239
remain open. Public ingress, registration/channel/task/bridge writers, operator
policy, fenced backup recovery and client rollout remain separate work.

## Composition and provisioning

`D1PollAdmission` takes one operator-supplied authoritative D1 binding and the
same explicit `origin`, `generation`, `policyRevision` and `policy` as SQLite.
Its constructor copies and validates configuration but performs no I/O. The
binding, options and ordinary/completion route are trusted composition inputs;
none come from request headers, payloads or a caller-selected bookmark.

The source-only interface is `prepare(rawJson, route)`, `commit(opaqueToken)`
and `recover(rawJson)`. All three are asynchronous. Tokens are instance-bound,
single-use and nonserializable; preparing never grants later write authority.
One caller-owned scope limits pending preparations and operations together to
eight. Keep that scope for the operation's lifetime; do not store it in Worker
globals or replace an uncertain instance as an automatic retry. Independent
instances share durable work and storage limits, but their in-flight bounds
and poisoned state are local, not distributed concurrency control.

The [unmounted HTTP composition](HTTP.md) uses trusted `{ read, signal }` input
to defer bounded body reading until after the durable charge. Route channel and
completion poll IDs must match the signed envelope. Plain string inputs retain
their existing behavior.

There is no runtime initializer. `D1_SCHEMA_OBJECTS` in `d1-sql.ts` is an
explicit **empty-fixture provisioning inventory**. Only the disposable test
Worker executes it and seeds synthetic keys/channels/authority. No method
creates, repairs, adopts or resets a database. The dedicated schema is not a
migration for production D1 or an existing standalone database. Its application
tables, indexes and triggers are pinned exactly. Only D1's own `_cf_KV` and
`_cf_METADATA` tables and SQLite's internal objects are outside that inventory;
other application objects, missing guards and changed definitions fail closed.

The D1 schema keeps the SQLite wire rows, generated logical byte costs,
accounting/capture/immutability triggers and mutually deferred root/control
foreign keys. Its final guard additionally advances the durable database clock
inside the last DELETE. A SQLite laboratory instance deliberately does not
accept this different guard definition. Runtime engine/pragma ownership differs:
D1 manages its engine and connections; the D1 adapter neither imports Node
SQLite nor changes journal, foreign-key or connection settings on a request.

## Work charge before protected work

Each operation first reads bounded pinned metadata from the primary, then
attempts one conditional `UPDATE … RETURNING clock` in a new primary session.
The update rechecks the entire metadata snapshot, schema, generation, policy,
database time and accounting window. It commits a maximum input/verification
charge in the operation's finite ordinary, completion or recovery lane **before
parsing the wire or verifying a signature**. No refund follows malformed input,
bad signatures, abandoned preparation, stale decisions or later rollback.

A competing charge or window change may make that CAS update affect zero rows.
The operation refuses with `busy`; it does not reread/rebase/retry or start
protected work. A thrown, malformed or lost storage response poisons the scope.
A late acknowledged charge also cannot start protected work. Failed requests
do not obtain reusable permits. More identities, channels or adapter instances
do not add allowance to the singleton authority row.

The charge accounts for at most `1 + history.records` signature attempts during
preparation and one during recovery. These are finite work-size allowances, not
a measured CPU budget, physical storage quota or public ingress protection.
The bounded metadata/admission I/O itself still needs an eventual ingress policy.
An invalid completion request consumes completion allowance and cannot use that
route to admit ordinary work or a close for another signed poll ID.

## One snapshot, then one guarded write batch

Cloudflare's [D1 batch contract](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)
provides transactional statements, not a JavaScript-interactive transaction.
Every standalone read/charge is the **first and only executed statement** of a
fresh [`first-primary` session](https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession).
The mutation batch likewise starts a fresh primary session. A reused session or
caller bookmark cannot supply authority: subsequent session reads may use replicas.

Preparation uses one SQL SELECT for pinned metadata, actor/channel policy,
exact receipt and any required root/control/history/registered keys. An indexed
`(channel, parsed pollId)` seek first materializes at most `history.records + 1`
rowids and scalar costs. Record/byte overflow returns metadata only, including
withholding the root payload. Parsed JSON node/depth/entry checks precede
canonicalization or cryptography. Records are separate bounded result rows,
not one potentially multi-megabyte JSON aggregate. The query respects D1's
[statement and function limits](https://developers.cloudflare.com/d1/platform/limits/),
including bounded compound SELECT groups in the tested native runtime.

The verified tally belongs to that captured snapshot. A post-cryptography
primary clock/configuration read checks freshness but never replaces the
captured revision. Commit first obtains one fresh primary snapshot of current
metadata, actor/channel/control, receipt, capture cursors and bounded retirement
references. An already committed exact receipt resolves before new poll
eligibility checks. Otherwise, the original service revision, complete actor
and channel state and poll control must still match. Even an ordinary message
on another channel changes the coarse service revision and fences the proposal.

The adapter derives a proposal and its costs itself, then sends one batch:

1. Stage the single transient guard only if the **complete current snapshot**
   still matches in SQL, schema/policy/generation are pinned, the message is
   absent and database time satisfies preparation and vote deadlines. The CAS
   includes metadata/work counters, actor, channel, control, capture cursors,
   active wake owner and affected retirement channels.
2. Conditionally update clock/window, reserve or convert the close allocation,
   insert the original wire message and exact receipt, and advance channel,
   actor and service counters. Every mutation requires that staged guard.
   Existing triggers capture eligible public-arrival/wake references and maintain
   their charges in the same transaction. Nothing runs as detached request work.
3. Select a bounded primary result snapshot. This also resolves an exact retry
   that another batch committed after preflight. Different signed content or
   retained unsigned metadata still conflicts; no storage/capture/sequence is
   allocated twice. A failed CAS with no receipt returns `stale` without replanning.
4. Execute the **last statement**, `DELETE … RETURNING id` on the guard. Its
   pinned trigger checks the independently calculated final message, receipt,
   control/history/reservations, ledgers, counters and capture cursors, plus
   policy/generation, preparation expiry and vote deadline using database time.
   It then advances the durable clock/window. Any failure rolls back the entire
   batch, including captures, receipts and all mutation charges.
5. Await and validate the **whole** batch, including the final deletion result,
   before interpreting any selected receipt. A missing mutation or an earlier
   statement's apparent success cannot be acknowledged independently.

A D1 batch failure is an uncertain storage outcome to the caller. The adapter
never parses driver error text into proof of rollback or absence, even when a
local fixture demonstrates rollback. The work charge committed before the batch
remains spent. A possible commit acknowledged after the local lifetime has
expired is withheld and poisons the instance; another instance may explicitly
recover the original operation. No storage attempt is retried automatically.

## Capacity, visibility and time

The [SQLite cost table](README.md#retained-capacity-and-completion) also applies
to these application rows: actual retained wire/receipt/reference bytes plus
fixed framing, preallocated control/counter rows and one 16-KiB transient guard
slot. Root admission holds four rows and 8,720 bytes for creator closure, plus
one history record, 2,576 history bytes and 32 history nodes. This allocation
includes eventual receipt and capture effects, not just the close envelope.

`used + reserved <= capacity` holds for both service and channel. Admission
checks the INSERT-before-eviction peak. Capture retirement credits its original
channel and service only; messages, receipts, controls, pinned keys and unused
close leftovers never retire here. Revotes retain every record. Deadline and
all-voted closure do not release reservations. These logical charges exclude
indexes, physical pages, platform metadata, replication and filesystem overhead;
they do not size a production D1 database or establish a billing/availability SLA.

Only enabled public channels without private ACLs accept new writes. Public
captures use the existing visibility predicate. A new encrypted `intel` writer
can receive its own initial ACK, but the record is excluded from public arrivals
and historical public receipt recovery. The separate wake capture uses the
64-KiB predicate and synthetic fixed active-owner set. It does not authorize or
test a live hook callback. No private-room or task-lease authority is involved.

Recovery charges its separate lane, verifies the raw original envelope against
the pinned full key, then reads one fresh receipt/key/current-visibility snapshot.
It checks freshness after asynchronous storage and before returning. Hidden,
nonpublic or unknown records return historical `unavailable`, which is neither
proof of absence nor permission for a new ID or replacement mutation. Exact
retries preserve all signed fields and the five retained metadata fields with
the existing absent/null equality; assigned relay positions and discarded
extensions are excluded. Historical receipts never become fresh authorization.

Database time drives deadlines and windows, not the author's timestamp. An
instance also retains its greatest observed database clock and checks monotonic
elapsed time. Preparations last at most five seconds, including charge latency.
The final SQL guard sees database time at that final step, not merely the earlier
preflight timestamp. This does not bound physical commit/acknowledgment latency
or forcibly interrupt already running storage/cryptography. Window rollover
renews only attempts. Changed generations fence old configurations; whole-backup
rollback with an unchanged generation is not detected or repaired here.

## Native evidence and remaining gates

Run the README's frozen installation/build/test commands. `pnpm test` includes
`test/d1-native.test.mjs` alongside the existing SQLite/process/model tests.
The native suite bundles the actual adapter into local workerd/D1 using the
Pages compatibility date and **no Node compatibility flag**. It checks that the
bundle has no external imports or SQLite/Noise/libsodium runtime. Parent-owned
fixture identities keep private keys in Node memory. Temporary listeners bind
only to loopback, outbound fetches are denied, and storage is disposable.
All initialization, arbitrary SQL, fault and inspection routes are test-only.

Native tests create actual D1 messages/receipts and cover last-slot/close races
in both orders, separate-request budget contention, a forced charge CAS miss,
simultaneous exact-retry batches, cross-channel fencing, complete bounded
history, every write-stage rollback, skipped mutations, final SQL deadlines,
reserved completion at storage/work exhaustion, capture peaks/retirement,
revotes, all-voted closure, schema/key/generation/clock failures, expiry during
awaits, lost acknowledgments and a full runtime restart without reseeding.
Independent-model differential checks compare receipts, signed records,
captures and tallies; the existing hosted D1 poll reader verifies these records.

These are local native tests, not remote replica-routing/commit-latency evidence,
production load measurements, a security audit or a reviewed restore procedure.
The runtime profile and full workspace checks must pass on the current PR head.
Production capture/registration/channel integration, every other ingress writer,
distributed concurrency/work policy, HTTP completion/recovery routing, client
pending-operation reconciliation, operator limits and a guarded rollout remain
release gates. Nothing here enables the public request-budget component.
